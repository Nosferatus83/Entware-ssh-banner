# 🧾 Entware SSH Banner for (Keenetic / other Entware OS)

Универсальный баннер для SSH с отображением состояния системы, пакетов Entware и сервисов с их состоянием.

Подсмотрено у https://github.com/OMchik33/Keenetic-Entware-banner и https://github.com/byrekrut/custom-banner-ssh-Keenetic
Но содержит гибкие параметры по определению сервисов в системе и их статусов

## 📁 Состав

В репозитории:

- `custom-banner.sh` — основной баннер
- `install_banner.sh` — установочный скрипт
- `banner.conf` — файл с конфигурацией для настройки точного определения Сервисов в системе и их статусов (при условии, что сервисы в /opt/etc/init.d реагируют на команду status)

---

## ⚡ Быстрая установка (обновление) (1 команда)

```bash
cd /opt/root && wget -q -O install_banner.sh https://raw.githubusercontent.com/Nosferatus83/Entware-ssh-banner/main/install_banner.sh && sh install_banner.sh -k
```

---

## ⚙️ Что делает установка

Скрипт автоматически:

- Устанавливает зависимости (`wget-ssl` и `whiptail`).
- Скачивает и настраивает `custom-banner.sh` и `banner.conf`.
- Всегда **перезаписывает** `custom-banner.sh` (свежая версия из репозитория).
- Для `banner.conf` реализована **гибкая логика** сохранения/перезаписи:
  - Если файла нет – скачивает.
  - Если есть – поведение зависит от переданных аргументов (см. ниже).
- Настраивает `$HOME/.profile` для автоматического запуска баннера при входе по SSH.

Добавляется:

```bash
. /opt/etc/profile
. /opt/root/custom-banner.sh
```

- Выводит в лог текущие параметры конфига и инструкции по изменению.

### ⚙️ Аргументы командной строки

При запуске установщика можно указать один из ключей, управляющих поведением с `banner.conf`:

| Аргумент           | Действие                                                 |
| ------------------ | -------------------------------------------------------- |
| `-f` или `--force` | Принудительно перезаписать существующий `banner.conf`.   |
| `-k` или `--keep`  | Оставить существующий `banner.conf` (не перезаписывать). |
| _без аргументов_   | Если терминал интерактивный – спросить пользователя.     |
|                    | В неинтерактивном режиме (CI) – **не перезаписывать**.   |

```bash

```

И убрать из `~/.profile` строку:

```bash
. /opt/root/custom-banner.sh
```

## 📝 Настройка после установки

Для удобства и точного определения сервисов и их статусов создан конфигурационный файл `banner.conf`. После установки вы можете отредактировать его по пути `/opt/root/banner.conf`:

- `SERVICE_MAP` – отображаемые имена сервисов (формат `имя_скрипта1:отображаемоеИмя1,имя_скрипта2:отображаемоеИмя2,` В конце списка обязательно ЗАПЯТАЯ).
- `PROC_MAP` – соответствие «имя скрипта» → «имя процесса» для `pidof`(формат `'имя_скрипта1:процесс1:имя_скрипта2:процесс2,` В конце списка обязательно ЗАПЯТАЯ).
- `POSITIVE_KEYWORDS` – ключевые слова, означающие **запущен** (разделитель `|`).
- `NEGATIVE_KEYWORDS` – ключевые слова, означающие **остановлен** (разделитель `|`).

После изменений выполните `source ~/.profile` или перезайдите по SSH.

## ❓ Часто задаваемые вопросы

**Вопрос:** Как вручную добавить новый сервис в баннер?  
**Ответ:** Сервисы сами определяются, но для красивого отображения и корректного определения статуса может потребоваться внести информацию в параметры `SERVICE_MAP` и `PROC_MAP` в файле `banner.conf`, затем перезапустите оболочку.

**Вопрос:** Почему баннер не обновляется после изменения конфига?  
**Ответ:** Убедитесь, что вы применили изменения командой `source ~/.profile`. При новом входе по SSH баннер автоматически перечитает конфиг.

**Вопрос:** Можно ли отключить баннер временно?  
**Ответ:** Да, закомментируйте строку `. /opt/root/custom-banner.sh` в файле `~/.profile`.

## 📌 Текущая логика работы и дорожная карта

### 🔍 Как определяются сервисы Entware

- **Сервисы Entware** – это скрипты, которые запускаются при старте системы через `/opt/etc/init.d/rc.unslung`.
- Баннер перебирает **все файлы-скрипты** из `/opt/etc/init.d/S*` и для каждого вызывает команду `status`.
- Анализ ответа происходит по следующему алгоритму:

1. **Поиск PID** – в выводе `status` ищется строка с `PID: ...`. Если PID найден, проверяется, существует ли процесс с этим PID.
2. **Поиск по имени процесса** – если в ответе нет PID или сам скрипт не поддерживает аргумент `status`, берётся имя файла (без префикса `S*`) и ищется **процесс с таким именем** через `pidof`.
   - В большинстве случаев разработчики называют скрипт так же, как и приложение, которое он запускает (например, `crond` → процесс `crond`).
   - **Для нестандартных имён существует маппинг** – сопоставление имени скрипта с реальным именем процесса (например, `xkeen` → процесс `xray`). Это задаётся в `PROC_MAP` конфигурационного файла.
3. **Анализ ключевых слов** – если процесс не найден, проверяются ключевые слова из `POSITIVE_KEYWORDS` (например, «запущен», «running», «alive»). Если такие слова есть, сервис считается запущенным.
4. **Итоговый статус** – если ни один из способов не подтвердил работу, сервис помечается как `❌ stopped`.

#### 📌 Важное замечание

Текущая реализация построена по принципу **«один сервис – один процесс»**. Для каждого скрипта проверяется не более одного имени процесса. Этого достаточно для большинства сценариев.

### 🗺️ Дорожная карта

Если проект окажется востребованным у сообщества, планируется добавить следующие возможности:

#### ✅ Режим «один сервис – много процессов»

- Например, `AWG Manager` может запускать не только свой основной процесс, но и дополнительный (например, `sing-box`). При этом **один сервис порождает два и более процессов**.
- Планируется реализовать проверку набора процессов для одного сервиса: баннер будет показывать статус каждого из них или обобщённый результат («все работают», «частично работает», «остановлен»).
- Это позволит **контролировать практически любой набор процессов**, связанных с одним скриптом.

#### 🧩 Гибкий маппинг

- Возможность задавать в конфигурационном файле несколько имён процессов через разделитель (например, `PROC_MAP="awg-manager:awg_manager,sing-box"`).
- Выбор режима отображения: общий статус (зелёный, если хотя бы один процесс жив) или детальный список.

#### 📈 Другие направления

- Улучшение парсинга вывода `status` – поддержка JSON или структурированных форматов.
- Асинхронная проверка сервисов для ускорения работы баннера (особенно когда сервисов много).
